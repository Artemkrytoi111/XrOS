## 2. Что потребуется для публикации

### 2.1 Домен — PLACEHOLDER, не выбран

Настоящего домена нет. Везде сейчас стоит `xros.example` (PLACEHOLDER:
домен не существует, это заглушка). Придумывать домен нельзя —
его должна назвать Мия.

Когда домен появится, заменить `xros.example` (PLACEHOLDER) в:

- `profile/pacman.conf` и `profile/airootfs/etc/pacman.conf` — `Server`
  в секции `[xros]`;
- `profile/profiledef.sh` — `iso_publisher`;
- `profile/airootfs/root/customize_airootfs.sh` — `HOME_URL`,
  `DOCUMENTATION_URL`, `SUPPORT_URL`, `BUG_REPORT_URL` в `os-release`
  и блок добавления секции `[xros]`;
- `packages/*/PKGBUILD` — поле `url=`;
- `repo/README.md`, `ARCHITECTURE.md`, `docs/REPO-PUBLISHING.md`
  (этот файл) — упоминания заглушки.

После замены прогнать `scripts/xros-diagnose.sh`: проверка §19з
требует, чтобы каждое упоминание `xros.example` (PLACEHOLDER)
сопровождалось пометкой PLACEHOLDER, — после появления настоящего
домена упоминаний заглушки остаться не должно вообще.

### 2.2 HTTPS-хостинг

- Статический файловый хостинг с HTTPS (сертификат обязателен:
  pacman проверяет TLS через curl, поэтому нужен валидный сертификат
  от публичного CA; самоподписанный не подойдёт без настройки).
- Публикуется каталог `repo/` целиком, с сохранением структуры:
  `xros/os/x86_64/*.pkg.tar.zst`, `xros.db.tar.gz`,
  `xros.files.tar.gz` (и `.sig`-файлы после шага 2.3).
- В `pacman.conf` первым `Server` становится
  `https://<настоящий-домен>/repo/$repo/os/$arch`;
  `file://`-снимок остаётся вторым (запасной источник для
  установки без интернета).

### 2.3 Подпись пакетов (GPG) — обязательна ДО включения обновлений

Без подписи публиковать репозиторий и тем более включать
автообновления НЕЛЬЗЯ: неподписанные пакеты может подменить
любой, кто контролирует сеть или зеркало.

Порядок работ:

1. Создать отдельный GPG-ключ только для подписи пакетов XrOS
   (не личный ключ разработчика, не ключ из другого проекта).
2. Подписывать пакеты при сборке (`makepkg --sign`) и базу
   при публикации (`repo-add -s` — создаёт `xros.db.tar.gz.sig`
   и подписи пакетов).
3. Перевести секцию `[xros]` в `pacman.conf` на
   `SigLevel = Required` (вместо нынешнего `Optional TrustAll`).
4. Выпустить пакет-связку ключей (по образцу `archlinux-keyring`):
   публичный ключ + `pacman-key --populate`, чтобы установленная
   система доверяла ключу подписи. Ключ должен попадать в систему
   через пакет из подписанного же репозитория (проблема «курица
   и яйцо» решается первичной установкой ключа из ISO).
5. Опубликовать отпечаток ключа в документации и проверять его
   при каждой смене ключа.

### 2.4 Публикация базы пакетов

- После каждой пересборки пакета: `makepkg` → обновить staged-копии
  → `repo-add -f repo/xros/os/x86_64/xros.db.tar.gz
  repo/xros/os/x86_64/*.pkg.tar.zst` (с `-s` после шага 2.3).
- Обновить ОБЕ копии: `repo/` и снимок
  `profile/airootfs/usr/share/xros/repo/` (иначе `file://`-источник
  в живой системе отстанет от `repo/`).
- Старые версии пакетов из каталога удалять (или держать
  максимум одну предыдущую для отката — решить при публикации).

### 2.5 Обновление ключей

- Ротация ключа: новый ключ подписывается старым (переходный
  период), публикуется заранее, старый отзывается только после
  того, как все системы получили новый.
- Отзыв скомпрометированного ключа: сертификат отзыва публикуется
  вместе с новым ключом; все системы должны получить обновление
  связки ключей до следующего обновления пакетов.
- Срок жизни ключа и дату ротации зафиксировать в этом документе
  при создании ключа.

### 2.6 Безопасная модель обновлений

- До публикации и подписи: обновлений из `[xros]` нет вообще.
  Пользователь обновляет Arch-репозитории вручную
  (`pacman -Syu` / `sudo xros upgrade`).
- После публикации И подписи: `xros-update.timer` можно включить
  отдельным шагом и только с явного разрешения. До тех пор таймер
  остаётся выключенным, а его юниты в пакете — инертными.
- Никогда: автообновление из неподписанного источника;
  автообновление с сервера-заглушки; `SigLevel TrustAll`
  на публичном сервере.

## 3. Чего НЕ делать

- Не включать `xros-update.timer`, пока репозиторий не подписан
  и не опубликован (см. 2.3, 2.6).
- Не выдавать `xros.example` (PLACEHOLDER) за рабочий адрес:
  в документации и конфигах он всегда сопровождается пометкой
  PLACEHOLDER, пока не заменён настоящим доменом.
- Не публиковать пакеты без подписи под видом «временно»:
  временный неподписанный репозиторий — это постоянный риск,
  системы начнут ему доверять.
- Не использовать ключ другого проекта и не подписывать пакеты
  личным ключом.
