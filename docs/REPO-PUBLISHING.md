## 2. Что потребуется для публикации

### 2.1 Домен — PLACEHOLDER, не выбран

Настоящего домена нет. Везде сейчас стоит `xros.example` (PLACEHOLDER:
домен не существует, это заглушка). Придумывать домен нельзя —
его должна назвать Мия.

Когда домен появится, заменить `xros.example` (PLACEHOLDER) в:

- `profile/pacman.conf` и `profile/airootfs/etc/pacman.conf` — `Server`
  в секции `[xros]`;
- `profile/profiledef.sh` — `iso_publisher`;
- `profile/airootfs/root/customize_airootfs.sh` — `HOME_URL`,
  `DOCUMENTATION_URL`, `SUPPORT_URL`, `BUG_REPORT_URL` в `os-release`
  и блок добавления секции `[xros]`;
- `packages/*/PKGBUILD` — поле `url=`;
- `repo/README.md`, `ARCHITECTURE.md`, `docs/REPO-PUBLISHING.md`
  (этот файл) — упоминания заглушки.

После замены прогнать `scripts/xros-diagnose.sh`: проверка §19з
требует, чтобы каждое упоминание `xros.example` (PLACEHOLDER)
сопровождалось пометкой PLACEHOLDER, — после появления настоящего
домена упоминаний заглушки остаться не должно вообще.

### 2.2 HTTPS-хостинг

- Статический файловый хостинг с HTTPS (сертификат обязателен:
  pacman проверяет TLS через curl, поэтому нужен валидный сертификат
  от публичного CA; самоподписанный не подойдёт без настройки).
- Публикуется каталог `repo/` целиком, с сохранением структуры:
  `xros/os/x86_64/*.pkg.tar.zst`, `xros.db.tar.gz`,
  `xros.files.tar.gz` (и `.sig`-файлы после шага 2.3).
- В `pacman.conf` первым `Server` становится
  `https://<настоящий-домен>/repo/$repo/os/$arch`;
  `file://`-снимок остаётся вторым (запасной источник для
  установки без интернета).

### 2.3 Подпись пакетов (GPG) — обязательна ДО включения обновлений

Без подписи публиковать репозиторий и тем более включать
автообновления НЕЛЬЗЯ: неподписанные пакеты может подменить
любой, кто контролирует сеть или зеркало.

Текущее состояние (A-40, 12.11.2026): production-ключ ещё НЕ создан —
приватного ключа подписи у проекта нет, и создавать его без
решения владельца НЕЛЬЗЯ. Поэтому `[xros] SigLevel = Optional`
(временно): это честный промежуточный режим — подписанные пакеты
проверяются, неподписанные принимаются. Публичный тестовый ключ
(`xros-gpg-test/xros-public.key`, отпечаток
`0EC935D2A8E31AEC1878BBE5797805A298A55BAA`) — ТОЛЬКО тестовый:
он больше НЕ копируется в живую систему и НЕ используется как
production. Единый источник истины для production —
`profile/airootfs/usr/share/xros/xros-gpg.conf`
(`XROS_GPG_PROD_FPR`, пока пуст = GPG не настроен).
Проверка ключа — `profile/airootfs/usr/local/bin/xros-gpg-check`
(формат, отпечаток, срок, отзыв, способность подписывать).
Импорт ключа — строгий, с проверкой отпечатка и падением при
любой ошибке: в живой системе (`customize_airootfs.sh`) и в
установленной системе (движок `xros_import_xros_key`).
Релизный ISO блокируется гейтом `scripts/build.sh --release`,
пока GPG не готов полностью.

Порядок работ (только владельцем, офлайн):

1. Создать отдельный GPG-ключ только для подписи пакетов XrOS
   (не личный ключ разработчика, не ключ из другого проекта,
   не тестовый ключ `0EC935D2…`):
   (PLACEHOLDER: `xros@xros.example` — адрес-заглушка для примера
   команды; домен `xros.example` пока не менять — решение владельца.)
   `gpg --batch --quick-gen-key "XrOS Project (XrOS Security Updates) <xros@xros.example>" ed25519 sign 0`
   Приватный ключ — ТОЛЬКО офлайн, на машине владельца.
   Его нет в репозитории, GitHub, build-env и ISO. Никогда.
2. Положить публичный ключ в `xros-gpg-prod/xros-public.key`
   (`gpg --export --armor <отпечаток>`) и записать отпечаток
   в `profile/airootfs/usr/share/xros/xros-gpg.conf`
   (`XROS_GPG_PROD_FPR`, 40 hex). Проверить:
   `profile/airootfs/usr/local/bin/xros-gpg-check xros-gpg-prod/xros-public.key <отпечаток>`.
3. Собрать dev-сборку (`scripts/build.sh --confirm`) — свежие
   пакеты в `repo/xros/os/x86_64/` (без подписей).
4. Подписать офлайн, на машине владельца:
   `scripts/sign-repo-offline.sh repo/xros/os/x86_64 <отпечаток>`
   — `gpg --detach-sign` для каждого пакета (`.sig`) и
   `repo-add -s` для базы (`.db.sig`, `.files.sig`), затем
   проверка всех подписей (`scripts/verify-repo-signatures.sh`).
   Ключ подписи для `repo-add -s` задаётся явно через `GPGKEY`
   (R-12; у repo-add нет флага --key). Неверный ключ ловится
   проверкой подписей на этом же шаге (fail-closed).
   Затем скрипт создаёт и подписывает manifest исходников
   (R-10, `scripts/make-sources-manifest.sh`): sha256 всех файлов
   `src/`, `branding/` и `PKGBUILD` пакетов —
   `repo/xros/os/x86_64/xros-sources.manifest` и
   `xros-sources.manifest.sig`. Manifest доказывает, что
   подписанные пакеты соответствуют текущим исходникам, без
   опоры на mtime (свежий git clone не роняет проверку).
   Приватный ключ при этом не покидает машину владельца:
   передаются только готовые `.sig` и публичный ключ.
5. Перевести секцию `[xros]` в ОБОИХ `pacman.conf`
   (`profile/pacman.conf`, `profile/airootfs/etc/pacman.conf`) на
   `SigLevel = Required` (вместо нынешнего временного `Optional`).
6. Собрать релиз: `scripts/build.sh --release` — гейт проверяет
   FPR, ключ, `Required` и все подписи; пакеты и БД при этом НЕ
   пересобираются (пересборка аннулировала бы подписи). Вместо
   прежней mtime-проверки свежести (R-10) релизная ветка шага 6
   проверяет manifest исходников
   (`scripts/verify-sources-manifest.sh`): подпись manifest
   production-ключом и побайтовое совпадение текущих исходников
   с manifest. Любое изменение, добавление или удаление исходника
   после подписания — FAIL: пересоберите с `--confirm` и подпишите
   офлайн заново (шаг 4).
7. Опубликовать отпечаток ключа в документации и проверять его
   при каждой смене ключа.
8. В будущем — выпустить пакет-связку ключей (по образцу
   `archlinux-keyring`): публичный ключ + `pacman-key --populate`,
   чтобы установленная система доверяла ключу подписи. Ключ должен
   попадать в систему через пакет из подписанного же репозитория
   (проблема «курица и яйцо» решается первичной установкой ключа
   из ISO — движок уже импортирует его в установленную систему).

### 2.4 Публикация базы пакетов

- После каждой пересборки пакета: `makepkg` → обновить staged-копии
  → `repo-add repo/xros/os/x86_64/xros.db.tar.gz
  repo/xros/os/x86_64/*.pkg.tar.zst` (с `-s` после шага 2.3).
  Фаза 5.1: опция `-f` убрана — pacman 7.1.0 её не поддерживает
  (`repo-add: invalid option -- 'f'`); без `-f` repo-add сам удаляет
  существующие записи и пересоздаёт их.
- Обновить ОБЕ копии: `repo/` и снимок
  `profile/airootfs/usr/share/xros/repo/` (иначе `file://`-источник
  в живой системе отстанет от `repo/`).
- Старые версии пакетов из каталога удалять (или держать
  максимум одну предыдущую для отката — решить при публикации).

### 2.5 Обновление ключей

- Ротация ключа: новый ключ подписывается старым (переходный
  период), публикуется заранее, старый отзывается только после
  того, как все системы получили новый.
  Конкретно (A-40): создать новый ключ офлайн (см. §2.3, шаг 1),
  положить его публичный ключ в `xros-gpg-prod/xros-public.key`,
  обновить `XROS_GPG_PROD_FPR` в `xros-gpg.conf`, переподписать
  весь репозиторий (`scripts/sign-repo-offline.sh`), собрать
  релиз (`scripts/build.sh --release`), опубликовать новый
  отпечаток; отозвать старый ключ только после того, как все
  установленные системы обновились на новый.
- Отзыв скомпрометированного ключа: сертификат отзыва публикуется
  вместе с новым ключом; все системы должны получить обновление
  связки ключей до следующего обновления пакетов. Проверка
  отзыва — `xros-gpg-check` (отвергает отозванный ключ).
- Срок жизни ключа и дату ротации зафиксировать в этом документе
  при создании ключа.

### 2.6 Безопасная модель обновлений

- До публикации и подписи: обновлений из `[xros]` нет вообще.
  Пользователь обновляет Arch-репозитории вручную
  (`pacman -Syu` / `sudo xros upgrade`).
- После публикации И подписи: `xros-auto-update.timer` включает
  установщик в установленной системе (только если `[xros]` подписан:
  production-ключ настроен И `SigLevel = Required` в секции `[xros]`;
  иначе таймер остаётся выключенным). Включение — отдельным шагом
  и только с явного разрешения. До тех пор таймер выключен,
  а его юниты инертны. Старый `xros-update.timer` из пакета
  `xros-cli` не включается никогда.
- Никогда: автообновление из неподписанного источника;
  автообновление с сервера-заглушки; `SigLevel TrustAll`
  на публичном сервере.

## 3. Чего НЕ делать

- Не включать `xros-auto-update.timer` (и старый `xros-update.timer`),
  пока репозиторий не подписан и не опубликован (см. 2.3, 2.6).
- Не выдавать `xros.example` (PLACEHOLDER) за рабочий адрес:
  в документации и конфигах он всегда сопровождается пометкой
  PLACEHOLDER, пока не заменён настоящим доменом.
- Не публиковать пакеты без подписи под видом «временно»:
  временный неподписанный репозиторий — это постоянный риск,
  системы начнут ему доверять.
- Не использовать ключ другого проекта и не подписывать пакеты
  личным ключом.
