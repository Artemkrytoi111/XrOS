## 1. Что такое XrOS

Профессиональный дистрибутив Linux на базе **Arch Linux** — настоящая
работающая система, а не концепт: живая система с KDE Plasma, графический
установщик своего дизайна, красивый GRUB, экран завершения с безопасной
перезагрузкой, диагностика и автотесты, проверка в QEMU.

Отдельный проект, не связанный с другими дистрибутивами. Основа —
официальные механизмы Arch Linux (`mkarchiso`, `pacstrap`, `pacman`,
`systemd`, GRUB). Никаких искусственных имитаций системных компонентов,
никаких AI/нейросетевых зависимостей, никаких программ «ради количества».

Имена по умолчанию (меняются одной правкой):

## 2. Откуда взят рецепт сборки (честно об источнике)

Архитектура опирается на рецепт, проверенный на практике при сборке
другого Arch-дистрибутива (AKVT OS, сборки 10–39). Из него берётся
только технология сборки, а не бренд, тексты или код один в один:
все файлы XrOS написаны заново под XrOS, следов другого проекта
в дереве нет (проверяется диагностикой, см. раздел 9; этот раздел —
только честное указание источника рецепта сборки).

### Основной путь сборки — ШТАТНЫЙ archiso (РЕАЛИЗОВАНО как рецепт, НЕПРОВЕРЕНО запуском)

```
mkarchiso -v -w work -o out profile
```

Никаких ручных обходов, маркеров `_run_once` и пропусков этапов:
искусственные маркеры, скрывающие невыполненные шаги сборки,
НЕ СОЗДАВАТЬ.

### Рецепт ручного pacstrap — НЕПРОВЕРЕН ДЛЯ XrOS, запасной путь

В другом проекте `mkarchiso` при `pacstrap` ПОЛНОГО списка пакетов
(~600) падал десятками тысяч ошибок `Write failed` + `EPERM`, хотя
ручной `pacstrap` того же списка работал всегда, а минимальный
`mkarchiso` — тоже. Это эффект масштаба/порога внутри `mkarchiso`,
а не ошибка списка. Проверенный там обход:

1. `rm -rf work out` — чистая рабочая папка и папка вывода.
2. **Ручной `pacstrap`** полного списка из `profile/packages.x86_64`
   в `work/` (не через mkarchiso).
3. `cp -a profile/airootfs/.` — файлы профиля в airootfs.
4. Запуск `customize_airootfs.sh` через `arch-chroot`.
5. Запись файла версии (`1.0`) вручную.
6. `touch` шести маркеров `base.*` (`_run_once`), чтобы mkarchiso
   пропустил уже выполненные шаги, включая сломанный pacstrap.
7. `mkdir iso/xros` + файл версии вручную (пропуск `_make_version`
   не создаёт их сам).
8. `mkarchiso` — только squashfs (zstd) + сборка ISO.

**Для XrOS этот рецепт НЕПРОВЕРЕН и НЕ считается гарантированным:**
список пакетов другой (43 пакета, KDE Plasma 6.8), версия archiso
другая, причина падения в другом проекте не установлена. На этапе
сборки СНАЧАЛА пробовать штатный mkarchiso; обход — только если
штатный путь воспроизводимо падает так же, и только после разбора
причины. **НЕ запускать вслепую.**

Готча:

- `customize_airootfs.sh` должен быть `+x` в профиле, иначе mkarchiso
  его не выполнит.
- Если mkarchiso берёт копию профиля из другого места (не из
  `~/workspace/xros/profile/`), правки синхронизируются и туда.
- При изменении загрузочных файлов удаляются не только 4 стандартных
  маркера, но и маркеры загрузки (`base._make_bootmode_*`,
  `_make_boot_on_*`).
- Хост сборки может подменять CA для egress-TLS
  (`CURL_CA_BUNDLE`/`SSL_CERT_FILE` → путь, которого нет в chroot):
  при сборке внутри chroot нужно бинд-монтировать актуальный CA
  и обновлять trust anchors перед каждым запуском pacman/curl.
- Скрипт-каркас: `scripts/build.sh` (только рецепт,
  запуск только с `--confirm` на этапе 10).
- Собственный build environment — `scripts/xros-build-env.sh`
  (финальная доработка 10.11.2026, зависимость от чужого chroot
  УБРАНА): свой каталог `build-env/`, rootfs из официального
  Arch bootstrap-тарболла (проверка GPG-подписи), `pacman -r`
  для пакетов, `systemd-nspawn` (запасной путь — `unshare`+`chroot`),
  `makepkg` от непривилегированного `builder`, `grub-script-check`.
  Статус (обновлено 10.11.2026, финальный этап): **rootfs СОЗДАН**
  (`build-env/root.x86_64` 3.2 ГБ, маркеры `init-done` +
  `deps-fetched`, builder uid 1000, rust/cargo 1.99.1, grub 2.16,
  pacman 7.1.0); Rust пересобран, все 4 пакета собраны от builder;
  `xros-build-env.sh` починен (4 бага). nspawn на хосте не работает —
  путь `unshare`+`chroot`. Проверки больше не зависят от чужого
  chroot. Подробно — `docs/final-refinement/build-env.md`,
  [AUDIT-REPORT.md](AUDIT-REPORT.md) §9.

## 4. Живая система: KDE Plasma 6.8 (Wayland)

### Что изменилось при аудите (РЕАЛИЗОВАНО в списке пакетов, НЕПРОВЕРЕНО в QEMU)

Plasma 6.8 **убрала X11-сессию полностью**: пакет `plasma-x11-session`
удалён из репозиториев Arch, `plasma-workspace` 6.8.2 с ним конфликтует
(проверено по archlinux.org 10.11.2026). Поэтому:

- Живая сессия — **Plasma (Wayland)**; X11-сессии больше нет.
- `plasma-x11-session` удалён из `profile/packages.x86_64`
  и из списков DE/удаления в `src/xros-install`.
- `xorg-server` оставлен в списке **временно**: в Plasma 6.8 от него
  ничего не зависит, кандидат на удаление после ретеста в QEMU.
- Прежняя причина держать X11 (чёрный экран Wayland в QEMU/bochs-drm,
  Plasma 6.4) требует **повторной проверки в QEMU** перед сборкой —
  см. раздел 10. Если Wayland в QEMU снова даст чёрный экран —
  пробуются `virtio-gpu`/virgl и modesetting; результат фиксируется
  честно, без выдуманного успеха.

### Как выглядит живой рабочий стол

- SDDM с автовходом пользователя `xros` (пароль заблокирован,
  вход — только автовход; sudo — NOPASSWD для установки).
- KDE Plasma: тёмная тема BreezeDark, тёмные иконки breeze-dark,
  обои `/usr/share/xros/wallpaper.png` (через `kdeglobals` +
  `plasma-org.kde.plasma.desktop-appletsrc` в домашнем каталоге
  и в `/etc/skel` — те же настройки получает пользователь,
  созданный при установке).
- На рабочем столе — заметный ярлык **«Установить XrOS»**,
  установщик также в меню приложений.
- Окно приветствия **автоматически появляется** после входа
  (только `/etc/xdg/autostart/xros-welcome.desktop` — штатный
  механизм KDE, работает и в Wayland, и в X11; один экземпляр —
  через `flock` внутри `xros-welcome-gui`; toggle «Запускать
  при старте» пишет `Hidden=true` в пользовательский
  autostart-файл; ручной запуск — из меню приложений,
  `xros-welcome-gui --manual`). **Финальная доработка
  10.11.2026:** удалены два параллельных механизма запуска —
  `systemd user xros-welcome.service` (с X11-переменными
  `DISPLAY=:0`/`XAUTHORITY`) и `~/.xprofile` (под Wayland
  не выполняется). Реальный запуск в Plasma Wayland —
  НЕПРОВЕРЕН, только в QEMU после сборки ISO.
- Никакой необходимости ставить KDE вручную, вводить команды
  в терминал или искать установщик.

### Безопасность живой системы

- Пароли `root` и `xros` заблокированы (`passwd -l`).
- `sshd` отключён на живой системе.
- `ufw`: `default deny incoming`, служба включена.
- `/etc/shadow` — `600`.
- SSH host keys живой системы не копируются в установленную
  (исключены из rsync + удаляются явно).
- `resolv.conf` живой системы не копируется (NetworkManager
  создаёт его при первой загрузке установленной системы).

### Архитектура установщика

- **GUI** (`src/xros-install-gui-rs`, Rust + egui/eframe): только
  собирает выборы и показывает прогресс. Работает в отдельном окне,
  не блокирует KDE. При запуске не от root — перевыполнение через
  `sudo` с сохранением `DISPLAY`/`WAYLAND_DISPLAY`/`XDG_RUNTIME_DIR`/
  `XAUTHORITY` (без `WAYLAND_DISPLAY` root-процесс под Wayland
  падал бы на XWayland; исправлено при финальной доработке
  10.11.2026).
- **Движок** (`src/xros-install`, bash+dialog): разметка, копирование
  системы, ядро, fstab, GRUB, пользователь, оболочка. GUI запускает
  его в неинтерактивном режиме (`XROS_NONINTERACTIVE=1`,
  конфиг `/tmp/xros-install.conf`, права 600, удаляется после чтения).
  Прогресс — в формате dialog-gauge (число + `XXX`-сообщения),
  журнал — в `/tmp/xros-install.log`.
- Консольный режим того же движка — полноценный интерактивный
  установщик (диалоги выбора диска, ФС, пояса, клавиатуры,
  пользователя, оболочки), а не заглушка.

### Безопасность установщика (РЕАЛИЗОВАНО, аудит 10.11.2026)

- Пароль/ФИО в chroot-heredoc экранируются `%q`
  (`printf -v ... %q`) — инъекция через пароль невозможна.
- Защита от установки на диск с ISO — и в авторежиме, и в ручном
  (проверка по `findmnt /run/archiso/bootmnt` + `lsblk PKNAME`).
- Проверка диска: `-b` и `TYPE=disk` (`lsblk -d -o TYPE`).
- `sudo --preserve-env=XROS_NONINTERACTIVE,XROS_INSTALL_CONF`
  (без него sudo стирает переменные и движок падает в интерактив).
- `umask 077` у движка; конфиг GUI `/tmp/xros-install.conf`
  создаётся с правами `0600` с момента создания.
- `machine-id` живой системы удаляется из установленной
  (`/etc/machine-id`, `/var/lib/dbus/machine-id`) и пересоздаётся
  через `systemd-machine-id-setup`.
- `resolv.conf` удаляется из установленной системы **после**
  всех сетевых операций в chroot (иначе pacman в chroot без DNS).
- Автовход: SDDM — `sddm.conf.d/autologin.conf` с сессией
  по выбранному DE (KDE — `plasma`, Sway — `sway`, не всем `plasma`);
  GDM — `/etc/gdm/custom.conf`; LightDM — свой конфиг.
  Перед включением выбранного DM **все** DM отключаются
  (sddm, lightdm, gdm) — иначе два DM дерутся за `display-manager.service`.
- Закрытие окна во время установки запрещено (`CancelClose`);
  кнопки навигации блокируются, пока идёт установка.
- `--step N` ограничен шагом 8 (`start_step.min(STEPS.len() - 2)`):
  на Finish (шаг 9) напрямую не попасть — только после
  реального `INSTALL_DONE`.
- **Защита дочернего процесса (РЕАЛИЗОВАНО, финальная доработка
  10.11.2026, тесты — `scripts/tests/test-child-process.sh`,
  33 PASS / 0 FAIL):** GUI отслеживает дочерний `xros-install`
  через `InstallHandle`; `pre_exec` ставит `PR_SET_PDEATHSIG
  (SIGTERM)` + проверку `getppid()` (закрывает гонку fork→prctl)
  + `setsid()` (своя группа процессов — для отмены и для внуков
  `rsync`/`arch-chroot`). Отмена: SIGTERM группе → 5 с →
  SIGKILL группе (`InstallHandle::cancel()` + `Drop`).
  Движок ловит `HUP`/`TERM`/`INT` ловушкой (`xros_on_signal`,
  идемпотентный `xros_cleanup`: гашение потомков, `umount -R`,
  удаление временных файлов, `sync`, причина в журнале,
  коды 129/130/143) + фоновый сторож родителя (PPID раз в секунду —
  bash откладывает ловушку, пока ждёт `rsync`/`mkfs`).
  Конфиг с паролями удаляется и при ошибке `spawn` в GUI.
  Кнопка «Остановить установку» — на шаге Install, с подтверждением;
  случайный крестик по-прежнему заблокирован (`CancelClose`).
  Не проверено без живой системы: реальное падение GUI посреди
  `rsync`, отмена кнопкой в реальном GUI — только в QEMU.

### Что делает движок (по шагам)

1. Разметка: UEFI — GPT (EFI 512M + корень), BIOS — BIOS-BOOT 1M +
   корень; ручной режим — форматирование выбранного корня,
   EFI только монтируется. ФС — `mkfs_root()`: ext4/btrfs/xfs.
2. Копирование живой системы rsync (исключая /dev, /proc, /sys,
   /tmp, /run, /mnt, кэш pacman, журналы, SSH host keys, gnupg).
3. Ядро и initramfs копируются с ISO (`/run/archiso/bootmnt/xros/boot/`),
   потому что в живой системе `/boot` пустой — без этого шага
   установленная система остаётся без ядра.
4. `genfstab -U`, hostname/hosts, locale, vconsole, localtime.
5. Удаление живых следов: archiso-конфиги, автовход SDDM,
   автостарт приветствия, живой пользователь `xros`, sudoers live.
6. `/etc/default/grub` + тема GRUB (копия из живой системы),
   `GRUB_DISABLE_OS_PROBER=false`.
7. В chroot: `locale-gen`, пользователь, пароли (chpasswd),
   sudoers wheel, NetworkManager, `mkinitcpio -P`.
8. GRUB: UEFI — `grub-install --target=x86_64-efi
   --efi-directory=/boot/efi --bootloader-id=XrOS`;
   BIOS — `grub-install --target=i386-pc`; затем `grub-mkconfig`.
   При падении `grub-install`/`grub-mkconfig` — явная ошибка,
   а не молчаливый успех; для BIOS/GPT заранее проверяется
   наличие раздела EF02.
9. Оболочка: KDE — уже скопирована, включается SDDM; другие —
   `pacman -S` из интернета, при неудаче честно остаётся KDE;
   `none` — **точный список удаления графики** (`XROS_GRAPHICS_PKGS`,
   15 пакетов: plasma-*, sddm, konsole, dolphin, pipewire*,
   wireplumber, xorg-server, шрифты, python-pyqt6, libxkbcommon-x11)
   + чистка сирот `pacman -Qtdq` + удаление `sddm.conf.d` и
   KDE-настроек из `/etc/skel` + проверка результата
   (`pacman -Q`: графики нет, база `linux grub networkmanager sudo
   openssh` на месте); цель по умолчанию `multi-user.target`,
   офис при `none` пропускается. **Финальная доработка
   10.11.2026**, тест `scripts/tests/test-de-none.sh` —
   58 PASS / 0 FAIL (до исправлений было 22/14). KDE:
   `plasma-desktop plasma-nm plasma-pa kscreen sddm konsole dolphin`
   (добавлены недостающие, `xorg-server` убран — Plasma 6.8 Wayland,
   он приходит зависимостью `sddm`). Все 7 вариантов DE реально
   реализуемы (проверено по sync-БД Arch). Реальная установка
   с `DE=none` — НЕПРОВЕРЕНО, только в QEMU.
10. Автообновления: **НЕ включаются** (см. раздел 13).
11. Офис: LibreOffice/Okular из интернета, без интернета —
    пропуск с предупреждением в журнале.
12. Автовход созданного пользователя (если выбран).
13. **Жёсткая проверка перед «Готово»**: ядро, initramfs,
    `grub.cfg`, тема GRUB, EFI-файл (`/boot/efi/EFI/XrOS/grubx64.efi`)
    или MBR-код, **непустой fstab**, пользователь в `/etc/passwd`,
    hostname, `display-manager.service` → выбранный DM.
    При провале — ошибка, а не экран успеха.
14. `sync`, `umount -R` целевого диска.

## 7. GRUB — тема XrOS (только GRUB, UEFI-only live-ISO)

- **Загрузчик — только GRUB.** `profiledef.sh`:
  `bootmodes=('uefi.grub')`. syslinux и systemd-boot удалены
  из профиля (см. раздел 3).
- **Почему live-ISO — только UEFI.** В archiso 92 режима
  `bios.grub` **НЕ СУЩЕСТВУЕТ** (проверено grep по `mkarchiso`:
  0 совпадений; есть только `bios.syslinux`, `uefi.grub`,
  `uefi.systemd-boot`). GRUB для BIOS-загрузки live-ISO штатно
  сделать нельзя. Поэтому live-ISO грузится **только по UEFI
  (GRUB)**; BIOS-загрузка live-ISO отсутствует. Установленная
  система на BIOS при этом GRUB получает штатно
  (`grub-install --target=i386-pc` в движке).
  Решение — за Мией (варианты в разделе 14).
- **Secure Boot НЕ поддерживается.** Нет подписанной цепочки
  (shim/MOK, подпись ядра и GRUB). Не заявляется нигде.
- Своя тема: `/usr/share/xros/grub-theme/theme.txt` — заголовок
  «XrOS 1.0», фон `grub-bg.jpg`, шрифты DejaVu Sans 14/16
  (`.pf2` лежат в теме, пути в `grub.cfg` — от корня ISO
  `/boot/grub/...`, а не `${prefix}`: `${prefix}` в live-GRUB —
  это memdisk образа GRUB, с ним шрифты/тема молча не находятся
  и меню становится текстовым).
- Выделение выбранного пункта: фон `#8B00FF`
  (`select_*.png`), текст `#F5F3FA` — контраст 5,39:1
  (было `#B66AFF` — 1,83:1, нечитаемо; исправлено 10.11.2026).
  Меню по центру (25%/30%, 50% ширины), полоса прогресса таймера
  автозагрузки, подпись «XrOS — на базе Arch Linux».
  Fallback-цвета без темы — `white/magenta`
  (`indigo` — невалидное имя цвета GRUB, исправлено 10.11.2026).
- Иконки классов: `xros`, `linux`, `windows`, `efi`, `memtest`,
  `reboot`, `shutdown` (кружки с буквами;
  рисованные иконки — следующим шагом).
- Live-меню (`profile/grub/grub.cfg`): XrOS, XrOS с экранным
  диктором, настройки UEFI, выключение, перезагрузка. Таймер 10 с.
  Тема подключается через `set theme=...`, при её отсутствии —
  простые цвета, а не ошибка. `loopback.cfg` переписан по образцу
  archiso releng (передаёт ядру `img_dev`/`img_loop`).
- **Memtest86+ и UEFI Shell в меню НЕТ** (финальная доработка
  10.11.2026): пункты удалены из `grub.cfg` и `loopback.cfg`,
  т.к. пакетов `memtest86+-efi` и `edk2-shell` в
  `profile/packages.x86_64` нет и файлы на ISO не попадут
  (пакеты существуют в Arch: `memtest86+-efi 9.00-1`,
  `edk2-shell 202608-1` — вернуть можно, добавив их в список
  пакетов и `menuentry` со стражем `search --file --set=`;
  проверки `-f` НЕ использовать — модуля `test` нет в UEFI-образе,
  см. ниже; инструкция — в комментарии в самих файлах).
- **Дефект UEFI `test`-модуля — ИСПРАВЛЕН (финальный этап,
  10.11.2026, проверено в QEMU):** в UEFI-образе mkarchiso 92 нет
  модуля `test`, поэтому все проверки `[ ... ]` там ложны: тема/фон
  не грузились, метка платформы была `x86_64-efi`, пункт «Настройки
  UEFI» скрыт (на BIOS `test` есть — там работало). Исправление:
  тема/фон грузятся **безусловно** (без `[ -f ... ]`), платформа
  и `fwsetup` — через **`regexp '^efi$'` / `'^pc$'`**.
  QEMU-подтверждение на настоящем `grub.cfg` (OVMF + SeaBIOS):
  ДО — 8–10 ошибок `test.mod not found`, текстовое меню, 4 пункта;
  ПОСЛЕ — 0 ошибок, меню с темой, заголовок `UEFI`, 5 пунктов.
  Эксперимент — `experiments/uefi-test-module/` (README, скрипты,
  логи ДО/ПОСЛЕ). `grub-script-check` обоих файлов — PASS
  (GRUB 2.12 хост + 2.16 chroot). Остаточный риск: список модулей
  UEFI сверен только чтением `mkarchiso` в чужом chroot;
  на исправление не влияет (см. [AUDIT-REPORT.md](AUDIT-REPORT.md) §9).
- Установленная система: `/etc/default/grub` (`GRUB_TIMEOUT=10`,
  `GRUB_THEME=...`, `GRUB_BACKGROUND=...`, `GRUB_GFXMODE=1024x768,auto`),
  `os-prober` включён — другие системы находятся и попадают в меню.
